# Подготовка к финалу

## Решение по инфраструктуре

Redis сейчас не добавляем. На проверенном VPS: 1967 МБ RAM, около 1145 МБ available,
нагрузка load average 0.04/0.09/0.08. Это снимок в момент проверки, не нагрузочный тест.
Один экземпляр Go API; PostgreSQL уже хранит талоны, сессии и outbox. Пул pgx ограничен
30 соединениями. Перенос очереди в Redis создаст второй источник состояния без
доказанной необходимости.

| Компонент | Решение | Когда пересмотреть |
|---|---|---|
| Redis | Не устанавливать сейчас | Несколько API-реплик требуют общего rate limiter или профилирование докажет пользу кеша |
| Kafka / RabbitMQ | Не устанавливать | Появятся независимые потребители событий, которые не покрываются outbox |
| Kubernetes / микросервисы | Не вводить | Несколько узлов и независимо масштабируемые сервисы |
| PgBouncer | Пока достаточно pgxpool | Суммарные пулы реплик приблизятся к лимиту соединений PostgreSQL |
| SSE | Следующий кандидат после замеров polling | Нужны меньшая задержка табло и меньше повторных чтений |
| GitLab CI | Добавлен | Frontend build/test и Go race/integration с отдельной PostgreSQL |
| Playwright | Добавлена проверка сценариев | Расширять по реальным пользовательским регрессиям |
| Prometheus / Grafana / Loki | Сохранить существующие | Настроить пороги по результатам нагрузочного теста |

Redis Pub/Sub не является заменой надёжной доставки: сообщения пропускаются при
отключённом подписчике ([официальная документация](https://redis.io/docs/latest/develop/pubsub/)).
Если понадобится кеш, состояние талонов остаётся в PostgreSQL; кеш допускает потерю
и восстанавливается. Перед выбором размера пулов учитывать суммарное число соединений
([PostgreSQL](https://www.postgresql.org/docs/current/runtime-config-connection.html)).

## Изменения

- Карта получает рабочие отделения из API; координаты из БД имеют приоритет.
  Сопоставление со старым каталогом возможно только по совпадающему адресу, не по ID.
- Текущая загрузка отделений обновляется каждые 15 секунд, максимум четыре запроса
  одновременно. Ошибка или просроченная оценка не превращается в нулевую очередь.
- Оценка ожидания основана на ожидающих/обслуживаемых талонах, открытых окнах и
  длительности последних завершённых обслуживаний. При недостатке истории используется
  явно отмечаемый в API норматив 300 секунд. Это оценка по отделению, не по услуге.
- Оценка дороги — расстояние по прямой при скорости 5 км/ч. Не обещает точное время
  пешеходного маршрута и не предсказывает приток новых посетителей.
- Получение талона по геолокации загружает услуги нужного отделения, не подменяет
  неизвестную услугу первой и сохраняет ключ операции при потере ответа.
- Для автоматического прибытия требуется свежая GPS-точка: расстояние + погрешность
  не превышают 20 м. При плохом GPS доступен обычный ручной сценарий.
- Tailwind собирается локально через PostCSS. Шрифты и Яндекс.Карты ещё требуют сети;
  при отказе карты остаются список и явно обозначенная схема.
- Администратор, оператор и демонстрация загружаются отдельными JS-частями.
- Причина отказа CallNext до наступления записи — NOT_ELIGIBLE_YET.
  Тесты раннего прихода согласованы с существующим правилом: раньше льготного окна
  посетитель становится доступен с рангом живой очереди.

## Демонстрационная сеть

Миграция 000020 добавляет nullable координаты и признак is_demo. Данные каталога
загружаются отдельно, только по явному решению оператора:

```bash
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < scripts/seed_demo_branches.sql
```

Скрипт добавляет все 25 отделений исходной карты под новыми стабильными UUID,
по три окна, существующие услуги и политику очереди. Названия начинаются с «Демо ·».
Повторный запуск не создаёт дубликаты и не меняет существующие талоны, отделения
или статусы окон. Исходное отделение Рязани сохраняется: всего становится 26.
Адреса, координаты и фото импортированы из исходного демокаталога; их внешняя
проверка не выполнялась. Это демонстрационная сеть, не интеграция с реальными ОПС.
Талоны и показатели нагрузки этой сети работают через настоящую БД.

## Проверки

```bash
(cd frontend && npm ci && npm test && npm run build)
(cd backend && CORE_TEST_DATABASE_URL='postgres://queueqa:queueqa@127.0.0.1:55432/queueqa?sslmode=disable' go test -race -count=1 ./...)
python3 qa/sprint4/openapi.py
# Playwright можно установить во временный каталог:
npm install --prefix /tmp/queue-browser playwright
/tmp/queue-browser/node_modules/.bin/playwright install chromium
# Отдельно запустить frontend: npm run dev -- --port 5181
node qa/sprint4/reliability-browser.mjs
```

Если локальный Docker продолжает использовать старые зависимости после изменения
`package-lock.json`, обновите только frontend и его анонимный `node_modules` volume:

```bash
docker compose up -d --build --force-recreate --renew-anon-volumes frontend
```

Браузерная проверка использует управляемые ответы API и GPS: точный/неточный GPS,
потеря ответа создания талона, повтор с тем же ключом, изменение живой рекомендации,
неизвестные координаты, отсутствие вымышленных рейтингов, мобильная ширина.
Интеграционный тест отдельно создаёт и вызывает талон во всех 25 демоотделениях
и проверяет идемпотентность загрузки каталога.

До крупного масштабирования нужно измерить стоимость опроса сети отделений.
При росте аудитории первым шагом будет пакетный endpoint текущей загрузки и
оптимизация SQL; установка Redis без этих измерений не обоснована.
